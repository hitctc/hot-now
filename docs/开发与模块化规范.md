## 2. 依赖方向

```text
页面 -> 组件 / composable -> service -> HTTP 路由 -> core -> repository / 外部服务
```

- 依赖只能从左向右；展示组件不得直接调用 service 或 HTTP。
- 路由处理器只适配 HTTP 协议、鉴权和输入输出；领域规则进入 `src/core/`，数据库读写进入 repository。
- `src/main.ts` 只负责运行时配置、数据库、锁、调度、监听和退出；`createServer.ts` 只负责 Fastify、全局配置、依赖装配和业务路由注册。
- 新模块仅接收实际需要的类型化依赖；不得传递巨大的全局依赖对象或通过隐式全局状态取依赖。

## 3. 源码目录与构建边界

| 目录 / 入口 | 稳定职责 |
| --- | --- |
| `src/main.ts` | 运行配置、数据库、运行锁、调度、监听与优雅退出；HTTP 依赖在 `src/app/createRuntimeServerDeps.ts` 装配 |
| `src/client/` | Vue 页面、组件、composable、主题和前端 service |
| `src/core/config/` | 非敏感配置与环境变量的运行时组装 |
| `src/core/source/`、`fetch/`、`topics/`、`report/` | RSS 读取、正文抓取、热点归并与报告生成 |
| `src/core/twitter/`、`hackernews/`、`bilibili/`、`wechatRss/`、`weibo/` | 各扩展来源的独立配置、采集、命中关系和候选映射；单个账号、关键词或 query 不写入 `content_sources` |
| `src/core/aiTimeline/` | 外部 Markdown feed 读取、解析、质量门禁和版本回退；不维护应用内官方源采集或事件入库 |
| `src/core/viewRules/` | 页面级筛选默认值、开关和持久化；不要新增平行配置源 |
| `src/core/pipeline/` | 采集、报告和发信的业务流水线；新增功能优先复用拆分后的 collection / mail pipeline |
| `src/core/scheduler/` | 既有运行时计时器；自动回调只读取 Hermes 阶段许可，不保存自动化状态 |
| `src/server/` | HTTP 协议、鉴权、页面分发和业务域路由；`createServer.ts` 只负责 Fastify 与路由装配 |
| `src/wechatResolver/` | 本地公众号 RSS 解析 sidecar |
| `tests/`、`deploy/` | 单元/轻量集成测试与生产模板 |

服务端使用 `tsconfig.json` 的 NodeNext 配置，源码内部导入必须保留 `.js` 扩展名。客户端使用 `tsconfig.client.json` 的 Bundler/Vite 配置，`.vue` 文件由 Vite 处理；不要把服务端模块解析约束套到客户端代码。

各来源、AI 时间线和 Hermes 自动化的业务语义分别以 `README.md` 与 [Hermes 自动化协作边界](./Hermes自动化协作边界.md) 为准；本节只定义代码放置位置。

## 4. 客户端边界

| 层 | 放什么 | 不放什么 |
| --- | --- | --- |
| `src/client/pages/` | 路由级编排、页面级组合和少量页面状态 | 表格、弹窗、重复表单和 API 细节 |
| `src/client/components/<domain>/` | 用户可理解的完整视觉/交互区域 | 跨区状态协调和直接请求 |
| `src/client/composables/` 或同域 `use*.ts` | 查询、分页、轮询、表单生命周期、异步状态和副作用 | 只为减少行数存在的转发层 |
| `src/client/services/` | 类型明确的 API 调用和请求参数转换 | 页面状态和 UI 条件 |
| 同域 `*Shared.ts` | 共享类型、列定义、格式化函数、选项 | 网络请求和可变页面状态 |

- 组件通过明确的 `props`/`emits` 协作，并保留稳定的 `data-*` 测试锚点。
- 内容反馈、创作弹窗/队列、监控和公众号配置的请求状态由同目录 `use<Component>.ts` 管理，组件只绑定展示与事件；组合式函数只返回模板、具名模板引用和明确公开接口需要的成员。
- `creativeApi.ts` 是兼容导出入口，实际请求分属 `creativeArticleActionsApi.ts`、`creativeImageApi.ts`、`creativeDraftPushApi.ts`、`creativeManualTextApi.ts`、`creativeAutomationApi.ts` 及既有列表模块；不得在兼容入口创建第二份缓存或工作流。
- 长文与短内容保持独立页面入口，只复用稳定组件和 composable；禁止用大量布尔参数做万能页面。成品页的列表/筛选/分页由同域 `useFinishedArticlesQuery.ts` 各实例独立管理，成品页及素材关联成品入口的详情身份、加载与过期响应由 `useFinishedArticleDetail.ts` 管理，成品页保存后重读沿用同一守卫，审核/推送/手工创建继续由各页面编排。
- 公共组件族由 `antdComponents.ts` 安装；表格消费者在自己的 setup 调用 `useTableComponent.ts`，按当前应用幂等安装原表格族，日期选择局部导入。不使用模块级“已安装”标志，不让公开页提前下载工作台依赖，不在安装器管理业务状态。
- 复杂页面先按完整功能区拆分，例如筛选、表格、编辑器、图片、预览、发布；不要按单个按钮或单个接口切碎。
- 短内容成品页由 `ShortFinishedArticlesPage.vue` 负责编排查询、动作和弹窗；状态选项、列定义、领域标签、北京时间与写作耗时格式化集中在同域 `shortFinishedArticlePresentation.ts`，保持为无网络副作用的展示模型；短表不展示素材趋势。

## 5. 服务端与核心层边界

- 路由以业务域组织，不按单个 endpoint 机械拆文件；域内再按稳定的读取、写入、图片、发布或监控边界拆分。
- 创作列表及详情的关联展示读取由 `creativeListReadRepository.ts` 组合既有素材/成品仓储；HTTP 路由只保留权限、参数、错误码和响应适配，不持有 SQL 或关联 JSON 解析。
- Hermes 队列展示的日期、历史和素材关联由 `creativeWriteQueueDisplayRepository.ts` 读取；它只补齐调用方拥有的展示快照，不修改共享缓存、任务或业务行。
- 旧页样式由 `sitePageAssetHelpers.ts` 按固定顺序拼接 `site.css` 与五个 `site.*.fragment.css`，浏览器仍只读取 `/assets/site.css`；调整边界必须保持响应字节、顺序与开发/构建回退。
- repository 按稳定读写职责拆分，保留兼容出口时不得改变既有导入契约。
- 迁移保持顺序、事务、幂等和历史 SQL 语义。`001`–`013` 与 `048` 起的新迁移按独立文件归档，`014`–`047` 整体保留在 `legacyMigrations014To047.ts`，由 `runMigrations.ts` 在原事务中按原顺序调用；后续真实变更继续使用独立迁移文件并由 `runMigrations.ts` 调度。
- 重构默认冻结 URL、HTTP 方法、请求/响应、鉴权、数据库字段语义和用户操作结果。

## 6. 文件规模与重构触发条件

行数是预警，不是验收目标：新增业务模块通常控制在约 500–600 行；复杂 Vue 页面或组件超过约 800 行时检查职责是否混杂。

只有出现以下任一信号才启动拆分：

1. 同一文件同时持有多个完整业务状态机；
2. 某项改动需要跨越不相关区域才能定位；
3. 相同表单、查询、轮询或展示逻辑已稳定重复；
4. 已有测试无法单独覆盖一个明确职责。

拆分前先写最小行为基线；拆分后保留用户行为和测试锚点。不能因为文件大就创建无业务名称的中间层，也不能为未来假设增加配置。

### 6.1 超过 1000 行文件的治理规则

- `src/` 与 `tests/` 中的代码文件超过 `1000` 行时，先建立完整清单并确认每个文件的稳定职责边界；一旦本次范围确认，清单内文件必须一次性治理，不拆成多个开发批次或多次提交。只有用户或维护者明确缩小范围时，才允许改变这个边界。
- 治理目标是职责清晰、依赖方向稳定和可独立验证，不是把所有文件机械压到某个行数。已经低于 `1000` 行且职责稳定的文件，不因数字继续拆分。
- 按完整功能区、业务域或稳定技术职责拆分；例如查询、表单生命周期、图片、发布、路由注册和测试夹具可以分别成模块。禁止按单个按钮、单个 endpoint（端点）或无业务名称的中间层切碎代码。
- 全量治理期间不得顺手修改无关业务、接口或格式；每个拆分单元都必须保留原有公开接口、鉴权、数据库语义、迁移顺序、浏览器资源行为和用户操作结果。

## 7. 测试、验证与发布

- 纯函数优先单测；composable 与组件覆盖关键交互；路由和 repository 使用少量跨模块集成测试。
- 局部改动先跑最相关测试；改动 `/settings/*` 客户端页面后，再跑 `npm run build:client`；改动启动、路由或运行时类型后跑 `npm run build`。
- 对外行为、任务链路或配置变更需要补最小 smoke test。
- 未通过相关验证不得提交或部署；发现既有失败必须单独记录，不能由重构掩盖。

### 7.1 一次性治理的验证与交付

针对一次性处理多个大文件的治理，验证必须覆盖整体结果，而不能只验证最后修改的单个文件：

1. 治理前记录相关定向测试或可重复的行为基线，治理后先运行定向测试，再运行完整测试套件。
2. 涉及客户端时运行 `npm run typecheck:client`；涉及服务端、路由、迁移或运行时装配时运行 `npx tsc -p tsconfig.json --noEmit`；涉及构建入口时运行 `npm run build`。
3. 运行 `git diff --check`，并重新扫描 `src/` 与 `tests/`，确认本次范围内不再有超过 `1000` 行的代码文件；低于阈值但职责稳定的文件不强行拆分。
4. 若拆分静态脚本，必须验证资源入口数量、加载顺序和必要时的字节级兼容；若触及迁移，必须验证事务、版本号、幂等性和数据库 `quick_check`；若部署，必须验证服务状态、健康接口和一个公网关键入口。
5. 代码规范、验证记录和本次范围说明在同一协作文档中维护，并与代码同批提交。验证未通过或存在未解释的回归时，不得提交、推送或部署。
6. 全部验证通过后，原则上使用一个语义完整的提交交付，提交说明包含目标、边界、变更文件和验证证据；推送和部署后再次执行生产健康检查，确保代码、远程分支和运行态一致。

### 7.2 按任务规模控制执行成本

目标是减少重复分析和操作往返，不增加固定仪式。先给简短计划与成功标准，后续只有事实、范围或风险变化时才调整，不为每个小步骤重新规划。

| 改动范围 | 最小充分流程 |
| --- | --- |
| 纯文档／规则 | 集中读取目标及直接相关规则 → 精确修改 → 差异、链接及一致性检查 → 项目要求的交付 |
| 局部逻辑／页面 | 集中定位数据与交互边界 → 最小实现和相关测试 → 第 7 节要求的类型／构建与适用现场验证 → 交付 |
| 跨模块或高风险 | 先确认接口、权限、状态和恢复边界 → 分段实现验证 → 适用专项门禁及安全部署 → 交付 |

- 上下文：先批量搜索入口、相关实现和测试；独立读取并行，依赖前一步结果的操作保持顺序。不反复读取已确认且未变化的内容，不为小任务重读无关历史或所有文档。长会话优先携带精简的现役事实，但不能丢失有效规则和未解决边界。
- 部署：尽早只读检查授权通道、受影响服务和活动任务；等待可与不依赖它的开发重叠。预检/冒烟先从当前路由和测试确认鉴权头、响应字段，并只读核对最新稿件版本后确定断言，不沿用旧会话状态猜当前数据。重启前再次确认安全。缺少能力时先报告真正阻塞，不反复登录或绕过鉴权；只重启受影响服务，不因文档或展示改动重启无关服务。
- 验证：同一源码状态已有充分通过证据时不无意义重跑；源码、配置或环境变化后重跑受影响检查。仍遵守现有测试、构建、部署和安全门禁，不能为缩短时间删断言、取消快照或跳过必要验证。
- 耗时：按分析定位、开发（含测试编写）、验证、等待、部署、提交及交付记录阶段起止与总耗时；有记录时另外区分模型响应、工具运行和用户待确认时间。并行时间只计一次，阶段与工具明细不重复相加。优先使用本轮时间戳和工具输出，不为计时反复扫描长会话或新增遥测；无法细分时标为估算或未知，不编造精确数字。
- 耗时数字只能来自时间戳或命令输出：交付说明里写分钟数前，先用会话记录中本轮用户消息的时间戳与当前时间算出实际间隔（一条只读命令即可），并写明未覆盖的部分（如本条回复自身的生成时间）。**不得凭“步骤多、感觉久”估出分钟数后写成阶段拆分**——那不是实测。无法实测时只写“未计时”，不写猜测值；历史计时偏差记录见[性能优化基线](./性能优化基线.md)。
- 汇报：结论、关键变化、验证／部署结果、残余风险及简要耗时优先；详细差异和计时留在可追溯记录中，不在每个阶段重复长报告。非阻塞的使用观察不升级为交付阻塞；安全及核心正确性问题仍须解决或明确报告。

同等规模局部需求可将 15～20 分钟作为优化参考，不是硬性承诺；跨模块、安全等待或部署时间单独说明。复用已验证构建产物、依赖未变时跳过安装及部署脚本分段计时，均属于后续工程优化：需另行实现、验证并同步部署手册；当前仍使用既定部署脚本，不凭本文绕过步骤或声称已完成优化。
