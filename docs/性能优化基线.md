# 性能优化基线

## 目标与范围

本轮优先覆盖 AI 新讯、AI 热点、公众号素材、短内容素材、成品文章、短内容成品、文章详情、写作队列状态及数据来源工作台。旧报告、历史页和控制台不进入第一轮。

验收目标：

- 常用列表首屏在 `1` 秒内显示数据。
- 翻页、筛选和刷新在 `800` 毫秒内完成。
- 文章详情在 `1` 秒内打开。
- 普通操作在 `300` 毫秒内给出明确反馈。
- 关键接口 P95 相对基线至少下降 `50%`。
- 不减少数据、不破坏跨项目接口兼容、不新增测试失败。

## 2026-07-31 生产基线

测试方式：从生产服务器本机连续请求五次，记录 Fastify 接口总耗时和响应字节数。数据库共 `7896` 条创作素材、`1216` 篇成品文章，SQLite 文件约 `282MB`。

| 接口 | 每页 | 耗时范围 | 响应大小 |
| --- | ---: | ---: | ---: |
| 公众号素材 | 50 | 916.8～1126.6ms | 807685 bytes |
| 成品文章 | 50 | 122.2～162.7ms | 2521679 bytes |
| Hermes 写作队列状态 | - | 50.8～154.7ms | 519 bytes |

短内容的正确方向值为 `short_content`；早期探测误用了 `short`，对应空结果不纳入基线。

## 已确认的瓶颈证据

1. 素材列表和成品文章列表都读取完整详情字段。素材包含 `full_content`、`raw_payload_json`，成品文章包含正文、人工稿、证据包、提示词、HTML 和阶段轨迹，导致列表响应达到数百 KB 至数 MB。
2. 素材默认查询只有独立的 `direction` 和 `created_at` 索引，SQLite 需要扫描同方向数据并创建临时 B-tree 排序。
3. 成品文章排序包含冗余的 `(pinned_at IS NOT NULL)` 表达式，现有 `direction, pinned_at, created_at` 索引无法直接完成排序。
4. 草稿推送成功次数的相关子查询只有单列索引，没有 `(article_id, status)` 复合索引。

| --- | ---: | ---: |
| 公众号素材 | 157.4ms | 2.8ms |
| 短内容素材 | 约 10ms（50 条） | 0.5ms |
| 成品文章 | 19.0ms | 8.5ms |

实验索引消除了两个核心列表执行计划中的临时 B-tree 排序。下一批仍需改为轻量列表模型，继续降低 JSON 解析、序列化、网络传输和 Vue 响应式处理成本。

## 2026-07-31 列表连接阻塞复盘

浏览器曾记录成品文章第 `21` 页请求总耗时 `36.51s`，其中连接等待（Stalled）为 `36.28s`，服务端响应等待只有 `229.40ms`。相同请求在生产服务器连续执行为 `65.5～129.1ms`，20 路并发最慢约 `1.29s`，因此不是列表接口执行了 36 秒。

根因证据：

1. 截图中第 `21` 页之前访问过第 `6` 页；该页有 `17` 张同域封面，总量约 `35MB`，中位数约 `2.08MB`，全部超过 `1MB`。
2. 单张封面通过公网下载曾约 `4.3s`；生产站只启用了 HTTP/1.1，大图会占用有限的同域连接，使后续 XHR 在浏览器连接池等待。
3. 写作队列状态代理同期出现过 `6.7s`、`8.9s` 和 `10.8s` 慢请求，进一步占用连接。
4. 勾选“显示已废弃”后，迁移 `46` 的部分索引不适用，查询需要临时排序；这只贡献约 `62～65ms`，属于次要瓶颈。

本批修复：

- 本地图片增加最大边长 `96px`、质量 `72` 的 WebP 缩略图。新图片上传时生成，历史图片首次访问时生成并原子缓存；失败只显示占位，不回退下载原图。
- 成品列表只加载缩略图，增加懒加载、异步解码和低请求优先级，点击预览时才读取原图。
- 四个核心创作列表在新请求开始时取消旧请求，只有最后一次结果可以更新页面。
- 写作队列状态使用服务端单飞和 `15s` 新鲜缓存，Hermes 最多等待 `3s`；失败时返回五分钟内最近一次成功状态并显示延迟标记，页面隐藏时暂停轮询。
- 迁移 `47` 增加覆盖全部成品的方向/置顶/创建时间索引；生产快照副本迁移约 `1.06s`，`quick_check=ok`，包含已废弃文章的查询不再临时排序，中位数约 `0.021ms`。
- Nginx 模板启用 HTTP/2，并提供备份、`nginx -t`、失败回滚和 reload 的一次性脚本；生产切换必须由具备 sudo 权限的用户执行。

## 监测约定

- 服务端默认只记录不低于 `500ms` 的慢请求，可用 `HOT_NOW_SLOW_REQUEST_MS` 调整。
- 每个响应包含 `Server-Timing`，便于在浏览器开发者工具区分服务端耗时和网络／前端耗时。
- 前端开发模式只在请求超过 `500ms` 时输出脱敏路径、状态码、总耗时和服务端计时。
- 正常快速请求保持静默，日志不包含查询参数、正文、Cookie 或密钥。

## 大文件治理的本次完成标准

本次“大文件优化”不以减少行数为验收目标。验收对象是代码边界是否清晰、业务逻辑是否保持不变、后续修改是否能定位到明确模块。只有同时满足以下条件，才算完成结构治理：

1. `src/server/createServer.ts` 只负责 Fastify 实例创建、全局配置/中间件、依赖注入和路由模块注册；具体业务处理器不再继续堆积在装配入口。
2. Vue 页面文件只负责页面编排、路由参数和页面级组合；请求、状态、轮询和副作用进入 composable（组合式逻辑），筛选栏、表格、状态单元格、展开区和操作区进入有明确输入输出的组件。
3. `ArticleDetailDrawer.vue` 按完整功能和视觉区域拆分，编辑器、标题同步、保存/专注、图片提示词、图片占位符、预览、审核和发布动作可以分别阅读和验证；不以“每个按钮一个文件”制造碎片。
4. 服务端路由按创作素材/成品、日报、监控、设置和 legacy 等业务域拆分；业务域内部再按稳定的读、写、图片、发布边界拆分，不按单个 endpoint（端点）机械切片。
5. 核心 repository（仓储）和迁移入口按稳定职责拆分；迁移顺序、幂等性、历史数据和外部 API 保持不变。
6. 每批拆分前有最小行为基线，拆分后通过相关单元/集成测试、类型检查、生产构建和必要的浏览器/API 冒烟；失败可独立回滚。
7. 公开 URL、HTTP 方法、请求/响应结构、鉴权、数据库字段语义和用户操作结果不改变；发现既有失败必须单独记录，不得用重构掩盖。

## 长期开发规范

- **先定义边界，再写代码**：新增或重构前先在本文件更新所属业务域、输入/输出、依赖和验证边界；地图未更新，不开始大范围拆分。
- **页面编排与业务逻辑分离**：页面保留路由、组合和布局；API 调用、查询参数、分页、轮询、乐观更新和错误处理进入 composable 或 service（服务）层。
- **组件按用户可理解的功能切分**：组件以筛选、表格、编辑器、预览、图片、发布等完整区域为边界，props/emits（属性/事件）显式定义；禁止用一个“万能页面”堆叠布尔开关。
- **服务端按业务域组织**：路由模块拥有清晰的依赖注入；handler（处理器）只负责协议适配，领域规则进入 core（核心层），数据库读写进入 repository，不在入口文件中跨层拼接。
- **核心层按稳定职责拆分**：读模型、写入、提示词、发布和迁移分别有可测试边界；不为追求小文件把一次事务拆成互相跳转的碎片。
- **依赖显式且最小**：新模块只接收实际需要的类型化依赖，不通过大型配置对象或隐式全局状态传递上下文。
- **测试镜像模块边界**：纯函数优先单测，composable 和组件覆盖关键交互，路由/仓储保留少量跨模块集成测试；重构不得删除原有行为覆盖。
- **不做无谓格式化和抽象**：不引入与本批目标无关的 lint（代码规范）工具链、全局格式化或未来假设型配置；行数下降只能作为结果，不能作为目的。
- **文档与代码同批更新**：HotNow 结构变化同步本文件；涉及公众号写作工作台时，同时更新 Hermes PRD 与决策记录。文档和代码不一致时先以代码事实为准，再修正文档。
